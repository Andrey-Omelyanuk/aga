# Варианты приложения по просьбе мейнтейнера

Плагинов нет. Приложение растёт так: мейнтейнер просит нейронку изменить
интерфейс или ядро, нейронка меняет код aga, собирает новый вариант —
интерфейс и ядро вместе — и поднимает его в отдельном namespace по отдельному
адресу рядом с работающим. Мейнтейнер проверяет вариант там и, если всё
хорошо, делает его рабочим. Базовые интерфейс и ядро, которые поставил внешний
админ, приложение удалить или изменить не может — это резерв: если вариант
сломался, через базу рабочий адрес возвращают и вариант чинят; сломалась сама
база — её чинит внешний админ.

Вариант стартует с копией данных, поднимает свои инстансы проектов и базу не
трогает: работа в варианте в базе не видна. Участник варианты не заказывает — он работает с проектами в том
приложении, которое сейчас рабочее. Вариант собирается из Dockerfile aga на
сборщике BuildKit внешнего админа и публикуется в registry из env — так же,
как образы проектов. Код варианта не ревьюим: его пишет сильная модель, и ей
доверяем полностью; решение мейнтейнера — делать ли вариант рабочим.

## Поведение
- по просьбе мейнтейнера нейронка собирает вариант приложения из изменённого кода
- у варианта виден дифф его кода против базы
- собранный вариант поднимается без подтверждения мейнтейнера
- каждый вариант живёт в своём namespace
- поднятый вариант открывается по своему адресу
- после подъёма варианта в чате, где его заказали, появляется адрес варианта
- при сбое подъёма в этом чате появляется причина сбоя с хвостом логов
- сообщение о сбое подъёма запускает нейронку чинить вариант
- после трёх неудачных подъёмов подряд (предел — env) нейронка останавливается и сообщает мейнтейнеру
- в чате мейнтейнера нейронка видит состояние подов варианта и события его namespace
- в чате мейнтейнера нейронка читает логи ядра и интерфейса варианта, включая упавший контейнер
- нейронка не может изменить ресурсы варианта напрямую — только пересобрать его
- ошибки браузера в интерфейсе варианта попадают в логи его ядра
- пока вариант не сделан рабочим, рабочий адрес ведёт на прежнее приложение
- мейнтейнер делает вариант рабочим, и рабочий адрес ведёт на него
- вариант, не прошедший проверку готовности, нельзя сделать рабочим
- базовое приложение всегда открывается по резервному адресу
- приложение не может удалить или изменить базовые ядро и интерфейс
- из базового приложения мейнтейнер возвращает рабочий адрес на базу
- падение варианта не задевает базовое приложение
- вариант стартует с копией данных рабочего приложения
- работа в варианте не меняет данные базового приложения
- ядро варианта не получает в k8s прав больше, чем у базового
- у базы и каждого варианта свой префикс namespace
- ядро варианта не может удалить или изменить namespace базы и других вариантов
- чат в варианте поднимает свой инстанс, инстансы базы вариант не трогает
- вариант работает с той же LLM, что задана базовому ядру
- в вариант входят той же учёткой SSO, что и в базу
- в чате участника нейронке недоступна сборка вариантов
- переключить рабочий адрес может только мейнтейнер
- удаление варианта удаляет все namespace его префикса, включая его инстансы
