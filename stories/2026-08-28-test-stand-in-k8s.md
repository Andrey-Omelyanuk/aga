# Тестовый стенд целиком в Kubernetes

Стенд, на котором я проверяю aga, поднимается в локальном кластере minikube:
ядро, Keycloak (SSO) и воркстейшны — всё в одном кластере. Docker Compose
больше не нужен: раньше им поднимали ядро как сервис, теперь это делает
kubectl — одного способа запуска стенда достаточно. Локальную разработку это
не трогает: `make run` (cargo run на хосте) остаётся как есть и работает без
кластера. Данные ядра — SQLite на PVC, отдельного сервиса БД нет. LLM для
стенда — внешний: ядро в поде ходит на адрес, достижимый из кластера.
Воркстейшны остаются как сейчас: под с git-копией и собственным Docker,
у агента нет доступа к k8s API; кластером управляет только ядро.

## Поведение
- `make k8s-deploy` поднимает стенд в кластере minikube: под ядра переходит в Ready и API отвечает на HTTP
- ядро, работая в кластере, по git-URL создаёт воркстейшн, и рядом с ним появляется готовый под `ws-<id>`
- команды агента воркстейшна выполняются внутри его пода, когда ядро работает в кластере
- данные ядра переживают перезапуск пода: после рестарта проекты, воркстейшны и сессии на месте
- на стенде поднят Keycloak: вход в веб-клиент идёт через него, у воркстейшна нет доступа к кластеру
- запросы к API с недействительным токеном отклоняются, с действительным — работают под участником
- стенд доступен извне через сервисы кластера: веб-клиент ядра и страница входа Keycloak отвечают
- `make k8s-verify` проверяет стенд, когда ядро работает в кластере, а не на хосте
- docker compose из проекта убран: `infra/compose.yml` и таргеты `run-d`, `stop`, `down`, `ps`, `log`, `reset`, `delete`, `sh` не существуют
