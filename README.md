# 🎬 aga — Ага, и готово.

> *«— Сделаешь?  
> — Ага.»*  
> *(Двое из ларца, одинаковых с лица, 1974)*

Платформа, где люди и LLM-агенты вместе работают над git-проектами через чат.
Участник открывает сессию: проект разворачивается на отдельной машине
разработчика (воркстейшне), а агенты набора выполняют задачи из чата прямо
в ней: читают код, запускают команды, правят файлы, задают вопросы людям.
Ядро — один Rust-бинарь, веб-клиент — React SPA, стенд — Kubernetes.

## 💡 Идеи

- **💬 Чат — единственная шина.** Задачи, ход работы агента, вопросы людям
  и ответы живут в чате. Агенты не вызывают друг друга напрямую и центрального
  оркестратора нет: участники (люди и агенты) общаются сообщениями.
- **🧠 Состояние — в чате, а не в процессе.** Процесс агента запускается на
  каждое сообщение-триггер и ничего не держит в памяти; контекст и история
  работы восстанавливаются из чата.
- **🛠️ Tools.** Агент вызывает инструменты через нативный function calling:
  `shell` — команда в Linux-окружении воркстейшна (разрешённые CLI — `git`,
  `cargo`, `npm`, `docker`… — задаются в наборе агентов) и `ask_human`. Для
  моделей без function calling — запасной текстовый режим. Плюс инструменты
  MCP-серверов из каталога: http (по url) или stdio (команда в воркстейшне).
- **🧹 Код проекта остаётся чистым.** Агенты, их промпты, скиллы и инструменты
  настраиваются в aga (наборы агентов), а не в репозитории проекта.
- **🌳 Территории.** Агенты набора образуют дерево по папкам проекта: читать
  можно всё (чужие изменения видны сразу), менять — только свою папку. Нужно
  чужое (коммит, общий артефакт) — просишь владельца в чате.
- **🤝 Human-in-the-loop.** Агент задаёт вопрос сообщением в чат и ждёт; любой
  участник отвечает на это сообщение — агент продолжает.

## ✨ Возможности

| Фича | Описание |
|------|----------|
| 💬 **Чат** | Сообщения, нити (дочерние чаты от сообщения), шаринг, команды `#invite`/`#kick`/`#end`/`#share`, сокращения `/имя`, live-обновление через Centrifugo |
| 🖥️ **Воркстейшны** | Под Kubernetes (стенд) или контейнер Docker (dev) со своим Docker (DinD) и копией проекта |
| 📂 **Сессии** | Проект + воркстейшн + владелец + чат; одна активная сессия на станцию; просмотр файлов и изменений (git diff) |
| 🤖 **Наборы агентов** | AgentSet на проект: дерево агентов, описание, скиллы из общего каталога (с историей правок), инструменты, LLM-подключение |
| 🔌 **MCP** | Каталог MCP-серверов (Streamable HTTP или stdio в воркстейшне агента); агенту отмечаются нужные — их инструменты приходят модели рядом с `shell` |
| ⚡ **LLM** | Любой OpenAI-compatible провайдер (Ollama, vLLM, OpenAI, LocalAI); подключения хранятся в БД, одно — дефолтное |
| 📊 **Трассировка** | SQLite (WAL): каждый шаг, команда, ответ LLM и вопрос человеку |
| 🔐 **SSO** | Keycloak: роли `participant`/`admin`, JWKS-проверка JWT |

## 🏗️ Архитектура

```
 Веб-клиент (front/, React SPA)
        │ REST + Centrifugo (WebSocket)
        ▼
 ┌──────────────────────────┐   события    ┌────────────┐
 │ aga — HTTP API           │────────────► │ Centrifugo │
 │ чат, проекты, сессии,    │              └─────┬──────┘
 │ наборы агентов, SSO,     │                    │ общий канал
 │ воркстейшны              │                    ▼
 └────────────┬─────────────┘        ┌─────────────────────────┐
              │                      │ aga agent — рантайм     │
              │   SQLite (WAL)       │ цикл: LLM → команды →   │
              └──────── общая БД ────│ выполнение → ответ в чат│
                                     └────────────┬────────────┘
                                                  │ kubectl exec / docker exec
                                                  ▼
                                     Воркстейшн ws-<id> (проект + DinD)
```

- `aga` — HTTP-сервер. Про агентов не знает: пишет сообщения и публикует
  события в Centrifugo.
- `aga agent` — рантайм агентов. Агент привязан к пользователю X и
  обслуживает его: когда X спрашивают (`@X`, сообщение в нити, которую начал
  X, ответ на вопрос агента), запускает цикл и отвечает от имени X. Шаги
  работы (команда + вывод) тоже публикуются в чат. Агенты общаются через чат
  как обычные участники; переписки ограничены нитями: глубина и число
  сообщений в нити задаются env `AGA_MAX_THREAD_DEPTH` (10) и
  `AGA_MAX_THREAD_MESSAGES` (100).
- `aga seed` — сброс БД и детерминированная тестовая фикстура.

## 🔄 Цикл агента

1. Рантайм получает сообщение, находит проект чата → набор → агентов, чьих
   пользователей спрашивают.
2. Промпт агента = описание + скиллы; контекст — сообщения чата: свои — как
   ответы ассистента (свои шаги — как вызовы инструментов), чужие — реплики
   участников с именами; в нити — её заголовок и исходное сообщение.
3. LLM отвечает вызовами инструментов (`shell`, `ask_human`, `start_thread`,
   инструменты MCP-серверов). В запасном
   текстовом режиме (флаг LLM-подключения) — блоками ```` ```bash ```` и маркером
   `[ASK_HUMAN]...[/ASK_HUMAN]`.
4. Каждая команда скрипта сверяется со списком инструментов агента, скрипт
   выполняется в воркстейшне (`sh -c`, пайпы и перенаправления можно) в
   песочнице владения: писать можно только в свою папку; вывод и код выхода
   возвращаются модели.
5. Повтор до финального ответа, вопроса человеку или лимита шагов. Шаги
   (команда + вывод) публикуются в чат.

## 🚀 Быстрый старт

Все команды — через `make` в корне (`make help` — список).

```bash
make init        # .env и main/config/roles.yaml из примеров
```

Dev-стенд без кластера (ядро + рантайм + Keycloak + Centrifugo + Ollama +
веб-клиент + воркстейшны `ws-1`/`ws-2` в docker compose):

```bash
make dev-up      # собрать и поднять стенд
make dev-seed    # тестовые данные (юзеры alice/bob, проекты, наборы, LLM)
make dev-verify  # проверка стенда
make dev-e2e     # e2e-сценарии (см. e2e/README.md)
```

Веб-клиент — `http://dev.<user>.localhost:<AGA_PROXY_PORT>`,
API — `http://api.<user>.localhost:<AGA_PROXY_PORT>`,
Keycloak — `http://auth.<user>.localhost:<AGA_PROXY_PORT>` (порт инстанса выводится
из `$USER`, см. `makefile`; `:80` на общей машине занят). Вход: `alice`/`alice-pass`
(participant), `bob`/`bob-pass` (admin).

Тестовый стенд в Kubernetes (minikube):

```bash
make k8s-up k8s-build k8s-load k8s-deploy k8s-wait
make k8s-seed
make k8s-dev     # доступ по *.localhost через локальный прокси
make k8s-verify  # e2e в кластере (см. e2e/README.md)
```

Локальная разработка: `make build`, `make run` (ядро), `make run-agent`
(рантайм), `make run-front` (vite), `make test`, `make lint`, `make fmt`.

## 🛡️ Безопасность

- Воркстейшн — изолированный под/контейнер без доступа к k8s API.
- Команды агента сверяются со списком инструментов и выполняются в песочнице
  владения (mount namespace станции): проект только на чтение, своя папка — на
  запись. Docker станции (DinD) общий и этой границей не закрыт.
- Лимит итераций на задачу; полная трассировка в SQLite.
- Учётки и роли — в Keycloak; воркстейшны создаёт только админ.
