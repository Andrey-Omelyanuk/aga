# Слабые места: агент ↔ чат ↔ workspace

Нумерованный список узких мест в связке агент ↔ чат ↔ workspace (обсуждение архитектуры).

1. **Последовательная обработка событий, один подписчик блокирует всех** (runtime.rs:119–139).
   События обрабатываются inline в SSE-цикле: `on_event().await`. Один долгий запуск агента
   (несколько итераций LLM + `kubectl exec`) останавливает обработку всех остальных
   каналов/сообщений. Очереди на воркстейшн и конкурентности нет.
   **Решено:** диспатч через `tokio::spawn`, семафор общего параллелизма (4), FIFO-мьютекс на
   пару «станция+агент», параллельные разные агенты станции, shared-инструменты (git/сборки)
   под мьютексом станции (`agent::SHARED_TOOLS`).

2. **ASK_HUMAN — тупик в чат-потоке** (agent.rs:180, server.rs:289).
   Агент возвращает строку `[WAITING_FOR_HUMAN] Request ID: N`, и рантайм постит её в чат как
   «ответ» (runtime.rs:224). `answer_human_request` (trace.rs:539) только меняет статус в БД —
   никто не возобновляет задачу после ответа. Человек видит сырой `Request ID: N`, ответ в чат
   не уходит, цикл не продолжается.
   **Решено:** вопрос публикуется в чат своим текстом (`AgentOutcome::Question`), задача —
   `waiting_human`; ответ — сообщение с `parent_id` на сообщение-вопрос от любого участника,
   он закрывает запрос (`answered`) и запускает продолжение того же агента (новая задача,
   контекст — чат). Ход работы с инструментами публикуется в чат: команда в `body`, обрезанный
   вывод в `hidden`. Мёртвые роуты `/human/pending` и `/human/answer/:id` удалены.

3. **Контекст — плоский `context_tail`, теряется всё** (chat.rs:779, runtime.rs:189).
   Агенту передаются только `body` последних 10 сообщений, склеенные через `\n`. Теряются:
   автор каждого сообщения, структура/нити, `title`, `hidden` (намеренно), ссылка на нить.
   «Сообщение-триггер» не отделено от истории — агент не понимает, к чему именно отвечать.

4. **Нет адресации — любое сообщение привязанного юзера запускает полный цикл**
   (runtime.rs:165, `message_should_trigger`).
   Триггер — только `origin=='user'`. «Спасибо», реплика другому человеку, служебное сообщение —
   всё вызывает LLM+exec. Нет способа сказать «это не тебе». `@Agent.<имя>` триггером не
   является, то есть и явного адресата тоже нет.

5. **Ответ подписывается личностью человека, а не агента** (runtime.rs:224,
   `send_message_with_origin(chat_id, author_id, ...)`).
   `author_id` — это слушающий пользователь. В чате ответ агента неотличим от реплики человека,
   кроме `origin`. Нет атрибуции к имени агента; если к юзеру привязано несколько агентов —
   непонятно, кто ответил.

6. **Один агент на пользователя, один набор на проект** (runtime.rs:174, `agent_listening_to`).
   Дерево агентов схлопывается до «того, кто привязан к автору». Нет маршрутизации по содержанию,
   нет координации/делегирования между агентами дерева при выполнении.

7. **Состояние станции не проверяется в момент запуска** (runtime.rs:195–200,
   `executor_for_workstation`).
   Открытие сессии проверяет `ready`, но путь агента нет: если станция `down` или сессия закрыта
   между сообщением и запуском, exec летит в несуществующий/освобождённый pod (проект уже
   очищен). Гонка актуальности workspace.

8. **Нет таймаута и отмены выполнения** (agent.rs:244, `execute_command`).
   `max_iterations` есть, а wall-clock лимита и abort — нет. Зависший `kubectl exec`/`docker exec`
   вешает единственный подписчик навсегда.

9. **Нет дедупликации/идемпотентности** (runtime.rs:141–151).
   При redelivery Centrifugo то же `message_id` обработается дважды → два запуска, два ответа.
   Защеты по `message_id` нет.
   **Решено:** `RuntimeState::seen` — повторная доставка того же `message_id` не запускает агента
   (тест `redelivered_event_triggers_single_run`).

10. **Пропасть при переподключении — события теряются** (runtime.rs:101–114).
    Привязки перечитываются при reconnect, но сообщения, опубликованные в разрыв SSE, не
    ретранслируются: нет backfill из БД. Сообщение, пришедшее, пока рантайм был отключён, не
    триггерит агента никогда.

11. **Внутренние ошибки утекают в чат** (runtime.rs:217).
    При падении цикла в чат постится `format!("Ошибка: {e}")` — сырые детали
    (`Command 'x' is not allowed`, сбои exec). В остальном API детали скрыты (500 без
    подробностей), здесь — наоборот.

12. **Безопасность команд — поверхностная эвристика** (agent.rs:274–292, `scope.write_allowed`).
    Бан `|><;&` ломает легитимные команды (`git log | head`, перенаправление).
    `base_cmd.starts_with("{tool}-")` — свободное совпадение. Tool из белого списка (`git`,
    `make`) может писать вне территории через свои аргументы/конфиг — граница держится только на
    парсинге строки.

13. **Трасса не привязана к сообщению чата** (runtime.rs:212).
    `task_id` — случайный UUID, не хранит `chat_id`/`message_id`. Из сообщения чата нельзя найти
    его trace, из trace — его сообщение. Поле «role» в `create_task` — первое слово промпта
    (agent.rs:129–133). Observability-разрыв.

14. **Треды вне контекста агента** (chat.rs:811+, runtime.rs).
    Сообщения нити живут в дочернем чате; `context_tail(chat_id)` берёт только текущий чат,
    `root_workstation_id` идёт к корню. Агент не понимает связи «нить ↔ родитель» и не видит,
    что отвечает внутри нити.

15. **Нет backpressure на `max_iterations`** (agent.rs:229–238).
    При исчерпании итераций в чат уходит бессмысленное «Task completed. Check trace for
    details.», хотя работа может быть недоделана.

16. **Прямой канал agent→workspace только через exec-команды** — правки файлов идут
    исключительно `sh -c`/exec со строкой-командой; нет структурного API записи (по design:
    write-эндпоинта нет). Для слабых LLM это плюс, но ограничивает: нельзя безопасно передать
    многострочный файл без ухищрений, которые режет бан спецсимволов (#12).
